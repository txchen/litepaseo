# Reproducible CPU and energy validation

Status: local LitePaseo baseline measured on 2026-11-11. The official-client comparison
and energy protocol below remain unexecuted; no energy savings are claimed.

## Local baseline, 2026-11-11

Application commit: `5f1e337a7b89de61126de4c018f56f2929bdc574`. Hardware: the test laptop,
Core Ultra 7 256V, 8 logical CPUs, 15.2 GiB RAM, AC connected, powersave governor.
Linux `7.2.13-200.fc44.x86_64`, Node `26.12.1`, headless Chromium `158.0.8127.18`.
The host was shared with other processes; thermal state and power policy were not
controlled. RAPL counters were unreadable. No real provider calls were made.

The built frontend used real HTTP/SSE and the application's BFF source, with two
in-process SDK facade doubles. BFF measurements include fixture generation and
logging; they exclude real daemon/provider costs. Each streaming host generated
a target 20 deltas/s (actual counts are recorded). Each browser context viewed one host. See the [harness methodology and
reproduction instructions](../benchmarks/README.md) for workload sizes and limitations.

The [primary run](../benchmarks/runs/2026-11-11T20-31-13.817Z/manifest.json) includes
environment, exact harness snapshots/hashes, event logs, counter samples and final
visible-message hash checks. [Summary and ranges](../benchmarks/runs/2026-11-11T20-31-13.817Z/summary.json)
and [per-repetition CSV](../benchmarks/runs/2026-11-11T20-31-13.817Z/counters.csv)
are generated by `benchmarks/analyze.mjs`.

CPU is percentage of **one logical core**, so 200% means two cores. Table values
are medians across three repetitions, except the 60-second idle case. Memory is
the median of sampled per-repetition peaks, not a continuous high-water mark.
Latency is the newest event marker to a post-mutation animation-frame callback,
sampled at most once per second/client; it is neither physical paint latency nor
the latency of every event. The p95 column is the median of per-repetition p95s.

| Workload | Browser CPU | BFF + fixture CPU | Browser peak PSS | Sampled p95 |
|---|---:|---:|---:|---:|
| Connected, no new events, running badges | 17.1% | 0.1% | 287 MiB | — |
| Plain streaming, one client | 34.7% | 1.4% | 299 MiB | 68 ms |
| Unfinished 12,000-line code fence, one client | 111.6% | 0.9% | 641 MiB | 177 ms |
| Plain streaming, eight contexts, 10,000 sessions | 267.6% | 2.2% | 1,592 MiB | 69 ms |
| 20 older pages loaded, then streaming | 40.2% | 1.3% | 431 MiB | 66 ms |
| 10,000 sessions, 50 directory updates/s | 24.0% | 0.9% | 297 MiB | — |

Navigation to the complete session count plus initial 60 messages took median
259 / 334 / 660 ms for 100 / 1,000 / 10,000 sessions. This excludes process launch,
login and BFF startup. The sidebar retained at most 22 rendered session rows in
these scenarios. Eight clients shared two upstream timeline subscriptions.

The large-code case produced 431–434 main-thread long tasks in each ~31.2-second
measurement window (30 seconds of generation plus drain), totaling 27.1 seconds.
Ordinary plain-text streaming produced no observed long tasks in its three runs.
The source reparses the entire growing assistant message and replaces its HTML on
each render (`TimelineRowView.vue` / `markdown.ts`); this is a likely source of the
large-message cost, although a parser/layout CPU profile has not isolated each part.

Loading older history left **2,066 message rows** rendered by the end of each run.
`App.vue` increases `shown` on pagination; the initial 150-row render window is not
a fixed virtual window. `TimelineStore.prepend` also has no independent retention
cap. A bounded history viewport that preserves scroll position is an optimization
candidate; the benchmark does not claim every pagination edge case is tested.

The hidden-signal case validates application unsubscribe/catch-up by overriding
`document.hidden`; it does not measure real browser background throttling. Directory
contents under churn, tool/approval rendering, input responsiveness, remote network
latency, macOS/mobile, official Paseo, and energy remain outside this baseline.

### Ten-minute streaming

All **27 primary cases passed** their final visible-message equality, page-error and
directory-stream cleanup checks. The ten-minute case used two clients and started a
new message every three deltas, crossing the designed browser retention threshold.
It generated 23,700 deltas in total and averaged 66.6% browser CPU and 1.3% BFF +
fixture CPU, with sampled p95 68 ms.
Each page retained at most **150 rendered message rows**. Internal browser-store row
counts were not directly instrumented.

| Minute | Browser median PSS | Combined browser JS heap | BFF + fixture median RSS |
|---|---:|---:|---:|
| 2 | 444.3 MiB | 12.1 MiB | 155.8 MiB |
| 5 | 450.3 MiB | 13.6 MiB | 155.5 MiB |
| 8 | 457.1 MiB | 14.7 MiB | 160.1 MiB |
| 10 | 460.0 MiB | 14.7 MiB | 162.9 MiB |

Browser PSS rose about 15.6 MiB from minute 2 to minute 10; the combined JS heap
leveled near 14.7 MiB in the last three minutes. This is bounded DOM behavior and
modest observed growth, **not proof of no memory leak**. The fixture deliberately
retains all generated rows, so server growth cannot be attributed solely to the BFF.
See [minute windows](../benchmarks/runs/2026-11-11T20-31-13.817Z/soak-memory.json)
and [raw samples](../benchmarks/runs/2026-11-11T20-31-13.817Z/soak-r1/samples.ndjson).

### Measurement corrections

A preliminary run was excluded from the reported results. Its process traversal
read only the main thread's Linux `children` file, missing Chromium's network
service; CPU/memory totals were therefore incomplete. The corrected sampler visits
every thread, and an independent [PPid-based audit](../benchmarks/runs/2026-11-11T20-31-13.817Z/process-tree-audit.json)
found no missing browser subprocesses. The preliminary large-Markdown case also
overran its intended duration because stopping waited for a delayed browser probe.
The corrected harness stops generation independently of probes. All reported short
scenarios were rerun after both fixes; no application performance change was made.

The excluded run, including its interrupted soak samples, is preserved in the
[preliminary diagnostic archive](../benchmarks/diagnostics/2026-11-11T20-11-40.812Z-preliminary.tar.gz).
It is not included in the reported medians. The
[frontend build audit](../benchmarks/runs/2026-11-11T20-31-13.817Z/frontend-build-audit.json)
records the served files' hashes and their comparison with a fresh production build.

### Animation diagnostic and optimization priorities

Three alternating-order pairs used the same 1,000-session fixture with running
badges, no new events and 20-second measurement periods. Enabling the existing
`prefers-reduced-motion: reduce` CSS changed browser CPU from median **16.8%**
(16.6–17.0%) to **0.2%** (0.1–0.3%). All six cases passed. This strongly implicates
the continuously animated status indicators in the observed idle CPU cost; the
experiment changes a browser media preference, not application source.
See [paired run results](../benchmarks/runs/2026-11-11T20-53-47.379Z-motion/summary.json).

Recommended implementation order:

1. Remove or redesign the continuously animated `box-shadow` status pulse. The
   existing reduced-motion setting already provides an immediate workaround.
2. Avoid reparsing and replacing the full growing Markdown message on every flush;
   investigate incremental code-block updates and batching, then rerun latency and
   long-task measurements to ensure the tradeoff is acceptable.
3. Keep history pagination in a bounded viewport with a preserved scroll anchor.
   Loading older history currently expands the rendered message count.

These are measured optimization candidates, not changes implemented by this report.

## Planned comparisons

Compare production builds of official Paseo web and LitePaseo on the same browser/device, plus official native separately if available. Record exact commits, browser/OS/Node versions, build flags, enabled plugins, daemon/provider versions, BFF placement, hardware, power mode, display brightness, refresh rate and thermal state. Run plugins off first, then a separately reported matched plugin scenario. Never compare different amounts of rendered content silently.

Use two layers. A deterministic fixture harness replays the same timestamped semantic timeline into each client's normal ingestion path (version-pinned adapters, no real model calls). Capture/sanitize one fixture and publish its hash, event count, bytes, durations and adaptation code. Validate equal final text, tool rows and approvals. This measures rendering/ingestion, not transport parity. A second two-daemon end-to-end run verifies transport and recovery with deterministic provider output where supported. If a mock provider cannot be installed without modifying official code, disclose that limitation and keep real-model runs exploratory because outputs vary.

Scenarios: 10-minute connected idle; 5-minute plain-text stream; 5-minute growing code/Markdown stream; large completed history plus new output; simultaneous output from two hosts; hidden tab for 5 minutes then foreground; one-host disconnect/reconnect; approval during streaming. Fix event cadence, text size, history size and exact scripted visibility/scroll/input actions in the fixture manifest. Include a long unfinished code fence and non-ASCII input.

## Procedure

1. Create a clean browser profile with extensions disabled. Fix screen/network/power conditions and background workloads. Place daemons off the measured laptop for the primary browser experiment.
2. Warm each production build for two minutes. Randomize A/B order in paired runs; run at least five pairs per scenario. Cool between runs to comparable temperature. Do not profile with DevTools open in the primary energy run.
3. Collect cumulative process CPU seconds before/after for the entire browser process tree, BFF and daemon separately. Report CPU seconds per wall second (one full core = 1), RSS/peak memory, network bytes, flush/parse/render counts, event-loop delay and browser long tasks. Account for shared browser processes consistently, preferably with only the test profile running.
4. Linux: use `pidstat`/process accounting for CPU, `perf stat` where available for context switches; use supported RAPL counters or an external power meter for joules. RAPL measures package domains, not process energy or whole-device energy. macOS: use supported Instruments/powermetrics workflows, separating Energy Impact scores from joules. Record tool versions, sampling interval, permissions and unsupported counters. Context switches are not interchangeable with hardware wakeups.
5. Measure idle baseline with the same instrumentation. Report raw and baseline-adjusted energy, measurement domain and elapsed time. For battery drain, use longer fixed-duration repeated trials with fixed initial charge bands; short percentage drops are too coarse. Use an external whole-device meter when practical, accounting for charging behavior.
6. Use the intended server-hosted BFF for the primary comparison; optionally run locally as a diagnostic. Report laptop energy and remote BFF CPU/energy separately; only sum comparable measured domains without double counting. Unknown daemon/remote energy stays unknown.
7. Record receipt-to-visible latency distribution, approval latency, final-state correctness, missing/duplicate rows and recovery time. A lower CPU value with lost events is a failed run.

Store `benchmarks/<run-id>/manifest.json`, fixture hashes, raw counter CSV, correctness results and analysis script. Suggested CSV fields: variant, repetition, scenario, wall_seconds, browser_cpu_seconds, bff_cpu_seconds, daemon_cpu_seconds, peak_rss_bytes, energy_joules, energy_domain, visible_latency_p50_ms, visible_latency_p95_ms, final_state_equal. Use null for unavailable measurements, never zero.

Report paired differences, medians, spread and confidence intervals with all failures disclosed. Tune batching at 250/750/1500 ms, holding all else constant. Compare Markstream with plain text and a baseline renderer, separately toggling highlighting/diagrams and history windowing to identify costs. Set an acceptance threshold only after establishing baseline variance and a user-acceptable latency budget. Source observations and renderer marketing are not measured performance evidence.
